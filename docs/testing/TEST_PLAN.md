# Test Plan — Local Mac Playground

| | |
|---|---|
| **App** | Local Mac Playground (`index.html`, `styles.css`, `script.js`, `theme-init.js`) |
| **Test tooling** | Playwright `@playwright/test`, `@axe-core/playwright`, `monocart-reporter` (coverage) |
| **Automation** | GitHub Actions workflow `Tests` (`.github/workflows/tests.yml`), required check `tests` on `master` |
| **Results** | Generated by CI for every run; see section 10. Not stored in the repo. |
| **Published reports** | [kerelle7.github.io/local-frontend-app/test-reports/](https://kerelle7.github.io/local-frontend-app/test-reports/) (`master` commits; [latest](https://kerelle7.github.io/local-frontend-app/test-reports/latest/)) |

## 1. Purpose

Catch regressions in the app's behaviour, accessibility and layout on every pull request, so changes can be merged with confidence. The suite is the safety net for the dark mode feature and the original click counter.

## 2. Scope

**In scope**
- Click counter behaviour.
- Light/dark theme: header toggle, saved choice, following the OS setting, and no flash of the wrong theme on load.
- Accessibility to WCAG 2.1 A/AA (automated checks with axe), including color contrast in both themes.
- Keyboard operation of the toggle.
- Layout at phone width (375px).
- Visual appearance (screenshot comparison) in both themes at desktop and phone sizes.

**Out of scope**
- Manual screen reader testing (VoiceOver, NVDA). Automated checks cover roles, names and states only.
- Performance and load testing.
- Browsers not shipped with Playwright (e.g. Edge, old Safari versions).

## 4. Test naming convention

All automated tests follow this convention, and every ID in section 6 matches a test title exactly.

- **Files:** `tests/<area>.spec.js`, one file per area.
- **Groups:** each file has one `test.describe('<AREA>: <area name>')`.
- **Test titles:** `TC-<AREA>-<NN>: <expected behaviour>`, for example `TC-THEME-06: a manual choice is kept on OS change when storage is blocked`.
- **IDs** are two-digit, sequential within an area, never reused or renumbered. Retired tests keep their ID reserved and are marked *Retired* in section 6.

| Area | Meaning | File |
|---|---|---|
| `CNT` | Click counter | `tests/counter.spec.js` |
| `THEME` | Theme toggle and persistence | `tests/theme-toggle.spec.js` |
| `FLASH` | Theme applied before first paint | `tests/no-flash.spec.js` |
| `A11Y` | Accessibility | `tests/accessibility.spec.js` |
| `RESP` | Phone-width layout | `tests/responsive.spec.js` |
| `VIS` | Visual appearance | `tests/visual.spec.js` |

Shared setup and helpers live in `tests/fixtures.js` (not a spec file). To run a single case: `npx playwright test -g TC-THEME-06`.

CI enforces this with `.github/scripts/check-test-ids.js`: the run fails if a title doesn't start with a valid ID, an ID is duplicated, or the IDs in tests and the table in section 6 don't match.

## 5. Approach and environments

- **Type:** end-to-end tests against the real page served by `python3 -m http.server 4173` (started automatically by Playwright).
- **Browsers (Playwright projects):** `chromium` (Desktop Chrome), `firefox` (Desktop Firefox), `webkit` (Desktop Safari), `mobile-safari` (iPhone 13). Every case runs in every project unless stated.
- **Defaults:** OS color scheme `light`, reduced motion on (turns off theme transitions so colors are final when asserted).
- **OS theme changes** are simulated with `page.emulateMedia({ colorScheme })`.
- **Blocked storage** is simulated by making `localStorage.getItem`/`setItem` throw.
- **Accessibility:** axe-core with tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, run after one click so the result text is checked, with the mouse moved away so normal (not hover) colors are measured.
- **Visual:** full-page screenshots compared with baselines in `tests/visual.spec.js-snapshots/`. Baselines are made on Linux Chromium in CI, because fonts render differently on macOS; the cases are skipped elsewhere.
- **Coverage:** V8 JavaScript coverage of `script.js` and `theme-init.js`, collected in Chromium.

## 7. Entry and exit criteria

**Entry:** the change is on a branch with an open pull request into `master`.

**Exit (required to merge):**
- The `tests` check passes: every case passes in every browser (skips listed in section 6 allowed).
- Line coverage of `script.js` + `theme-init.js` is at least **90%** (enforced by `.github/scripts/test-summary.js`).
- Any new behaviour has a new test case, added to section 6 with the next free ID.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Flaky timing (e.g. paint timing read too early) | Tests wait for conditions instead of fixed delays; CI retries failures up to 2 times and reports them as flaky. |
| Automated accessibility checks miss issues | Treat axe as a baseline; do a manual screen reader pass for larger UI changes. |
| Screenshot differences from fonts or OS | Visual cases run only on Linux Chromium in CI, against baselines made there. |
| Hover or transition states give wrong colors | Mouse moved away before axe; reduced motion disables transitions. |
| Tests only run when someone remembers | Required `tests` check on `master` blocks merging until they pass. |

## 9. Running the tests

**Locally** (needs Node.js and Python 3):

```bash
npm ci
npx playwright install
npm test
```

- `npm test -- --project chromium` runs one browser; `npx playwright test -g TC-THEME-06` runs one case.
- `npm run report` opens the HTML report. Coverage: `reports/coverage/index.html`. Full report with coverage: `npx monocart show-report reports/monocart/index.html`.

**Updating visual baselines** (after an intended visual change, or for a new `VIS` case):
1. Delete the affected PNGs in `tests/visual.spec.js-snapshots/` (or add the new test) and push.
2. The CI run fails those cases with "snapshot doesn't exist" and uploads the new screenshots as the `visual-baselines` artifact.
3. Download it (`gh run download <run-id> -n visual-baselines -D tests`), review the images, commit and push.

**In CI:** the `Tests` workflow runs on every pull request, on pushes to `master`, and on demand (Actions → Tests → Run workflow).

## 10. Test artifacts

**Principle:** what we *intend* to test lives in the repo and is reviewed with the code. What a *run* produced is generated by CI for that commit and published outside the repo. Reports are never edited by hand or committed.

**Stored in the repo** (versioned with the code, changed through reviewed PRs):

| Artifact | Where |
|---|---|
| Test plan | `docs/testing/TEST_PLAN.md` (this file) |
| Test code and config | `tests/`, `playwright.config.js`, `.github/` |
| Visual baselines | `tests/visual.spec.js-snapshots/` |

**Generated by CI for each run** (tied to the commit that was tested):

| Artifact | Where to find it | Kept for |
|---|---|---|
| Results summary | Comment on the pull request, updated on every run; also the workflow run's summary page | Life of the PR / run logs |
| Published report per `master` commit | [GitHub Pages `/test-reports/`](https://kerelle7.github.io/local-frontend-app/test-reports/): an index of runs, `/test-reports/<commit-sha>/` per commit (summary, HTML report, coverage, JUnit), and `/test-reports/latest/` | Latest 50 `master` commits |
| HTML report | CI artifact `test-reports` → `reports/html/` | 30 days |
| JUnit XML | CI artifact `test-reports` → `reports/junit.xml` | 30 days |
| Coverage | CI artifact `test-reports` → `reports/coverage/` (HTML, `lcov.info`, `coverage-summary.json`) | 30 days |
| Failure evidence | CI artifact `test-reports` → `test-results/` (screenshots, traces) | 30 days |
| New visual baselines | CI artifact `visual-baselines` (see section 9) | 30 days |

**How publishing works:** every push to `master` is tested and published. Master runs are never cancelled or merged together. Two jobs in `.github/workflows/tests.yml` run after the tests, whether they passed or failed:
1. **`publish reports`** adds that commit's reports to the `test-reports` branch using `.github/scripts/build-report-site.js`. If another run published at the same time, it starts again from the latest history and retries.
2. **`deploy pages`** deploys GitHub Pages:
   - the app from the current tip of `master` at the site root;
   - the report history under `/test-reports/`.

   It always builds from the latest state, so re-running an old commit adds its report without putting an old app live.

Runs are listed by commit date, newest first, so a re-run of an old commit doesn't become "latest".

The `test-reports` branch holds generated files only. Don't edit it by hand, merge it, or delete it: deleting it erases the report history.
- **Single commit:** every publish replaces the branch with one commit holding the current reports. The history lives in its folders, so old commits add nothing, and the branch's size stays bounded at about the size of the 50 kept reports.
- **Force pushes:** CI replaces the branch with `--force-with-lease`, which only succeeds if no other run has changed it in the meantime. Any protection on the branch must therefore block deletion but **not** force pushes. PR runs are not published; their reports stay as run artifacts.

**Defects** found by tests are tracked as GitHub Issues, or described in the PR that fixes them.
